SIF Watch — System Architecture

An AI-powered early-warning system that analyzes workplace safety reports to detect precursors of serious injury and fatality incidents.

Overview

What SIF Watch does

Workers submit free-text safety reports. An LLM classifies each report's risk level, hazard category, and justification. The system then tracks SLAs, clusters similar incidents, detects anomalies, and surfaces urgent items to safety officers.

🔍 Classify

Gemini LLM reads each report and outputs risk level (high/medium/low), hazard category, and a one-sentence justification.

📊 Aggregate

Dashboard charts show hazard frequency, high-risk trends, and recurring problem sites. Anomaly detection flags sudden spikes.

🚨 Act

SLA deadlines trigger alerts. Human overrides let experts disagree with AI. Audit logs track every change for accountability.

AI Pipeline

LLM classification pipeline

The /analyze endpoint tries multiple Gemini models in order, with JSON response mode. If all models fail, a rule-based fallback classifier kicks in.

1
Build prompt
Insert site, role, report text into classification template
2
Try models
gemini-3.6-flash → 3.5 → flash-latest → 2.5-lite → 2.5
3
Parse JSON
Strip markdown fences, extract {risk_level, hazard_category, justification}
4
Fallback
If all models fail, keyword-based classifier provides estimate
Photo cross-check: When a photo is uploaded, the system sends both the image and report text to Gemini Vision, asking if the visual evidence is consistent with the described hazard.

Clustering

Semantic report clustering

After each analysis, the system checks if the new report is similar to existing ones. Similar reports share a cluster ID, shown as "clustered" badges on the reports table.

How similarity is measured

Step 1 — Semantic hash: Keywords map reports to categories (fall_heights, electrical, chemical, vehicle, equipment, general).

Step 2 — Text overlap: Tokenize both texts, compute Jaccard similarity. Threshold: ≥0.25.

Step 3 — Assign cluster: If similar reports exist, reuse their clusterId. Otherwise create a new one.

→ {

Anomaly Detection

Weekly spike detection

Compares each site's report count and high-risk count this week against its 3-week historical average. Sites with 2×+ spike are flagged.

Example output: "Metro Industrial Park: 4 reports this week (avg: 1.3/week). 4 high-risk this week (avg: 0.3/week)" — flagged as anomaly because both counts exceed 2× the historical average.

Triggers anomaly when:

  • • This week's reports ≥ 2× historical weekly avg
  • • This week's high-risk ≥ 2× historical weekly avg
  • • Minimum threshold: ≥3 total or ≥2 high-risk

Where it appears:

  • • Red banner at top of /dashboard
  • • Lists each flagged site with counts
  • • Auto-fetches on page load via GET /api/reports/anomaly-check
Scoring

Site safety score formula

score = clamp(0, 100, 100 − (highRiskCount × 15) + speedBonus)
Penalty
Each high-risk report costs 15 points
Bonus
Faster resolution earns up to 30 bonus points
Recalculation
Triggered on every status or risk change
Score ≥ 80 = Safe
Score 50–79 = Watch
Score < 50 = At Risk
