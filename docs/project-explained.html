1. The Problem

🚧 Current State of Workplace Safety

In construction, manufacturing, and industrial sectors, safety reports are filed on paper or via scattered emails. Critical hazards go unnoticed, responses are slow, and there is no data-driven way to identify recurring risks at specific sites. By the time a pattern is detected, injuries have already occurred.

4. Feature Deep-Dives

4.1 AI Risk Analysis & Reasoning Highlights

What it does: Every new report is automatically analyzed by an AI model (via Groq API) that classifies its risk level, assigns a hazard category, generates a human-readable justification, and extracts key danger phrases from the text.

📝 Report filed
→
🤖 Groq AI classifies
→
📊 Risk + Category
→
⏰ SLA calculated
→
📋 Tasks generated
→
📱 SMS sent (if high)

How AI Analysis Works

When a report is filed, a fire-and-forget background job starts immediately (the report returns to the user instantly without waiting). The background job:

  1. Sends the report text to Groq API with a carefully crafted prompt that asks for: risk_level (high/medium/low), hazard_category (one of 8 types), justification (1-2 sentence explanation), and key_phrases (danger words found in the text).
  2. Tries multiple AI models in sequence: openai/gpt-oss-120b → qwen/qwen3.6-27b → openai/gpt-oss-20b. If one fails or is rate-limited, the next is tried automatically.
  3. Extracts structured JSON from the AI response, stripping markdown fences and parsing the classification result.

AI Reasoning Highlights (Key Phrase Extraction)

The AI identifies key danger phrases from the report text and stores them. On the report detail page, these phrases are highlighted in yellow within the report text, so safety officers can instantly see what triggered the classification. For example:

"Strong chemical fumes detected in paint booth area. Ventilation system appears to be malfunctioning. Workers complaining of headaches and nausea."

This is powered by two mechanisms: (1) the AI extracts key_phrases in its JSON response, and (2) a regex-based fallback in helpers.ts scans for high-risk patterns like /(?:unguarded|exposed|live)\s+(?:wire|electrical|edge)/gi and medium-risk patterns like /(?:not\s+wearing|missing\s+(?:helmet|hardhat))/gi.

Fallback Classification (When AI is Down)

If all Groq models fail, the fallback classifier in fallbackAnalysis() kicks in. It uses keyword matching on the report text:

  • High risk keywords: "fall", "unguarded", "exposed wiring", "confined space", "forklift" + "pedestrian", "almost hit", "loose", "wobbly"
  • Medium risk keywords: "not wearing", "missing", "damaged", "spill", "ventilation", "exit blocked"
  • Default: low risk / procedural gap

The hazard category is also inferred from keywords: "electrical/wiring" → Electrical, "forklift/vehicle" → Vehicle/Traffic, etc.

4.2 Category-Based SMS Alerting via Textbee

Problem: When a high-risk hazard is detected, the right people need to be notified immediately — but different hazard types need different responders. An electrical hazard should alert the Electrical department, not the Chemical Safety team.

Solution: Admins configure SMS recipients per hazard category in the Admin → SMS Recipients tab. The system also supports an "All Categories" option for safety officers who need to know about everything.

How Textbee Works

Textbee turns your own Android phone into an SMS gateway. The flow:

  1. Install Textbee app on an Android phone with a SIM card
  2. Register the device on textbee.dev and get an API key
  3. Our server sends an HTTP POST to Textbee's API with the message and phone numbers
  4. Textbee's server pushes the message to your Android phone via WebSocket
  5. Your phone sends the actual SMS through the cellular network
  6. Status changes from "pending" (queued) → "sent" (delivered by phone)
High-risk report analyzed
→
Query SmsRecipient table
WHERE category = report.category
OR category = 'All Categories'
→
Collect phone numbers
→
Textbee API call
POST /api/v1/gateway/send-sms
→
Android phone sends SMS
→
AuditLog records
"SMS sent to Electrical, Fire Dept"

Key Implementation Details

  • E.164 format required: Phone numbers must be +919876543210 (country code + number, no spaces). Both client (HTML pattern) and server (regex /^\+[1-9]\d{6,14}$/) validate this.
  • Multiple recipients: One category can have multiple phone numbers. All receive the same alert simultaneously.
  • Fallback to env: If no SMS recipients are configured for a category, the system falls back to SAFETY_OFFICER_PHONE from the .env file.
  • Audit trail: Every SMS send attempt (success or failure) is logged to AuditLog with the department names (not phone numbers) for privacy.
  • Offline phone required: The Android phone must be online with Textbee app running. If the phone is off, messages stay in "pending" status until it reconnects.

SMS Message Format

🚨 HIGH RISK ALERT: Metro Industrial Park — Electrical. Exposed wiring near water pipe creates electrocution risk.

4.3 Safety Reports

What it does: The central hub for viewing, creating, and managing all hazard reports. Workers file reports here (or from the field via offline mode), and safety officers review and triage them.

Report Table Features

  • Risk badge column: Color-coded badges — High Medium Low. Shows "override" tag if a human reviewer changed the AI's classification.
  • Report text column: Shows truncated report text (60 chars + ellipsis) with full text on hover tooltip.
  • Site dropdown: Select from existing sites or choose "+ Add new site" for a new location. Prevents typos and duplicate site names.
  • Sort dropdown: Toggle between "Sort by Risk" (high first) and "Sort by Recent" (newest first). Click-outside closes the dropdown.
  • Expandable rows: Click any row to expand and see the full report text, AI justification, override info, and a "View full details" link to the report detail page.
  • Cluster visualization: Toggle the "Clusters" button to show which reports are semantically similar (e.g., two reports about "exposed wiring" at the same site get clustered together).
  • Anonymous reporting: Checkbox hides the reporter role. The report still shows the site and hazard info, but the reporter identity is hidden.
  • CSV bulk upload: Upload a CSV file with columns reportText, site, reporterRole to create multiple reports at once. Useful for importing historical data.

Report Detail Page

Click "View full details" to see:

  • Report text with highlighted key phrases — danger words highlighted in yellow
  • AI justification — the AI's reasoning for its classification
  • Regulatory compliance — which Indian laws apply to this hazard type
  • Corrective tasks — auto-generated tasks assigned to departments with due dates
  • Activity log — complete audit trail with IST timestamps (e.g., "Analyzed by Groq AI at 23/08/26 15:01")
  • Status dropdown — change from Pending → Analyzed → Acknowledged → Resolved
  • Risk override — human reviewer can change the AI's risk assessment with a reason

4.4 Admin Center

What it does: The command center for safety managers. Three tabs cover task management, report triage, and SMS configuration.

Tab 1: Task Board (Kanban)

A drag-free kanban board with three columns: Open → In Progress → Done. Features:

  • Auto-assignment: When tasks are auto-generated by AI, they're assigned to the matching department. E.g., an Electrical hazard task goes to the Electrical department, a Structural hazard to Structural.
  • Department filters: Filter the board by department (Traffic & Vehicles, Electrical, Structural, etc.) to focus on your team's work.
  • Priority badges: Each task shows its priority (URGENT / HIGH / NORMAL / LOW) with color coding.
  • One-click transitions: "Start work" moves Open → In Progress. "Mark done" moves In Progress → Done.
  • Due date tracking: Overdue tasks are highlighted in red.

Tab 2: Reports

Filterable report list with site and risk-level filters. Create corrective tasks inline per report — the department is auto-assigned based on the hazard category, and you can override it.

Tab 3: SMS Recipients

Configure which phone numbers receive SMS alerts for each hazard category. Features:

  • Category dropdown with 8 hazard types + "All Categories"
  • E.164 validation on both client and server (rejects invalid phone formats)
  • Multiple recipients per category — e.g., both the Electrical department head and the safety officer
  • Name field — optional label (e.g., "Fire Department") shown in audit logs instead of phone numbers

4.5 Dashboard & Analytics

What it does: A real-time analytics dashboard showing the organization's safety posture across all sites. Updated on every page load (server-rendered).

Summary Cards

Three at-a-glance metrics: Total Reports, High Risk count, Pending Action count. These update in real-time as reports are filed and resolved.

Anomaly Detection

The system compares each site's this week report count against its historical 3-week average. If a site has 2x or more its normal volume (or 2x high-risk reports), it's flagged as an anomaly with a red banner at the top of the dashboard. This catches sites that are suddenly becoming more dangerous.

threshold = max(historicalAvg × 2, 3 reports)
if thisWeekCount ≥ threshold → ANOMALY DETECTED

Heinrich's Law Escalation Scoring

Based on Heinrich's Law: for every 1 serious injury, there are 29 minor injuries and 300 near-misses. SafeSignal applies this principle by scoring each site's escalation risk based on its hazard mix over the last 30 days.

How the Escalation Score Works

Escalation Score = (highRisk × 10) + (mediumRisk × 3) + (lowRisk × 1)

Classification:
  Score > 40  → 🔴 Critical  (immediate intervention needed)
  Score ≥ 20  → 🟡 Elevated  (close monitoring required)
  Score < 20  → 🟢 Normal    (manageable risk level)

The scoring weights reflect Heinrich's insight: high-risk reports are 10x more indicative of escalation than low-risk ones. A site with many low-risk reports is concerning, but a site with even a few high-risk reports is a red flag for potential serious injury.

Example: Metro Industrial Park has 5 high-risk, 3 medium-risk, and 2 low-risk reports in 30 days.

Score = (5 × 10) + (3 × 3) + (2 × 1) = 50 + 9 + 2 = 61 → 🔴 Critical

Regulatory Compliance Flags

For each active hazard category, the system shows which Indian regulations apply. This helps safety officers understand their legal obligations. See section 4.9 for details.

Hazard Category Frequency (Bar Chart)

A bar chart showing how many reports fall into each hazard category. Helps identify which types of hazards are most common across the organization.

High-Risk Reports Over Time (Line Chart)

A 30-day line chart showing daily high-risk report counts, bucketed by IST dates. Spikes indicate periods of increased danger that may need investigation.

Recurring High-Risk Sites

Sites with 2 or more high-risk reports are listed with their count. These are sites that need immediate attention — recurring high-risk reports suggest systemic problems, not one-off incidents.

4.6 Site Safety Scoreboard

What it does: Ranks all sites by their safety score (0–100). Higher = safer. Creates healthy competition between sites and makes it easy to identify the most dangerous locations.

Scoring Formula

Score = 100 - (highRiskCount × 15) + speedBonus

where speedBonus = max(0, 30 - avgResolutionHours / 2)

How It Works

  • Every site starts at 100 (perfect safety score)
  • Each high-risk report costs 15 points — 7 high-risk reports zero out the score
  • Speed bonus rewards fast resolution: If you resolve reports quickly (low avgResolutionHours), you earn up to 30 bonus points. A site that resolves high-risk reports in 2 hours gets +29 points.
  • Score is recalculated every time a report is resolved (via recalculateSiteScore())

Visual Design

Sites are ranked with medal emojis for top 3 (🥇🥈🥉). Each site shows a progress bar colored by score: green (≥80), yellow (≥50), red (<50).

4.7 Interactive Map

What it does: Displays all reported hazards on a map view with risk-level color coding. Each pin shows the site, hazard category, date, report text, and AI justification on click.

Useful for identifying geographic clusters of hazards — e.g., if multiple reports come from the same area, it may indicate a systemic issue at that location.

4.8 Active Alerts (Stale Report Detection)

What it does: Monitors for high-risk reports that have been sitting too long without resolution. If a high-risk report has been in "pending" or "acknowledged" status for more than 48 hours, it appears on the Alerts page.

How It Works

SELECT * FROM SafetyReport
WHERE riskLevel = 'high'
  AND status IN ('pending', 'acknowledged')
  AND reportedAt < NOW() - INTERVAL '48 hours'
ORDER BY reportedAt ASC  -- oldest first (most overdue)

Each alert shows how many hours overdue it is (e.g., "72h overdue") and a "Review" button to jump directly to the report detail page. This ensures no critical hazard is forgotten.

4.10 Offline-First Reporting (PWA Support)

Problem: Construction sites, mining operations, and remote industrial areas often have poor or no internet connectivity. Workers can't file hazard reports from the field, which means dangerous conditions go unreported until someone gets back to the office — by which time it may be too late.

Solution: SafeSignal uses IndexedDB (via the idb library) to create a local offline queue. Workers can file reports even with zero connectivity.

How Offline Reporting Works

Worker fills report form
→
Check navigator.onLine
→
If offline → save to IndexedDB
→
Toast: "Saved offline"
→
When online → auto-sync

Technical Implementation

  1. Detect connectivity: The form checks navigator.onLine before submitting. If false, it imports the enqueueReport() function from lib/offline-queue.ts.
  2. Save to IndexedDB: The report payload (reportText, site, reporterRole, isAnonymous) is stored in an IndexedDB object store called pendingReports. IndexedDB persists even if the browser is closed.
  3. Show confirmation: A toast notification appears: "Saved offline — will sync when connected". The form closes and the user can continue working.
  4. Auto-sync on reconnect: When navigator.onLine becomes true again, the queue is processed. Each pending report is submitted to POST /api/reports and removed from IndexedDB on success.

Why IndexedDB (Not localStorage)?

  • Storage limit: IndexedDB can store hundreds of MBs vs localStorage's 5MB limit
  • Async API: Won't block the main thread
  • Structured data: Supports objects and indexes, not just strings
  • Reliable: Data survives browser crashes and restarts

4.11 AI-Powered Task Generation

What it does: Automatically generates 1-3 corrective tasks for every analyzed report. Tasks are specific, actionable, and assigned to the right department.

How It Works

  1. AI extracts tasks using the TASK_EXTRACTION_PROMPT — a carefully crafted prompt that asks the AI to generate concrete actions like "Install temporary fall protection barriers" rather than vague ones like "investigate".
  2. Tasks are auto-assigned to the matching department. The mapping: Electrical → Electrical dept, Structural/Fall Hazard → Structural dept, Chemical Exposure → Chemical Safety dept, etc.
  3. Priority matches risk: High-risk reports get urgent/high tasks, medium-risk get high/normal, low-risk get normal/low.
  4. For high-risk reports, the system generates 3 tasks: (1) immediate safety action, (2) root cause fix, (3) follow-up inspection within 24 hours.

Fallback Task Generator

If the AI fails, fallbackTaskExtraction() generates tasks based on hazard category keywords. For example, an electrical hazard automatically generates: "De-energize and lockout affected electrical system" (urgent) + "Inspect and remediate root cause" (high) + "Schedule follow-up inspection" (normal).

4.12 Natural Language Query

What it does: Users can ask questions about their safety data in plain English and get natural language answers.

How It Works

  1. User types a question: "How many high-risk reports at Metro Industrial Park this week?"
  2. System fetches all report data (site, date, risk, category, status) and serializes it as JSON
  3. Both the question and data are sent to Groq AI with a prompt: "Answer using ONLY the data provided"
  4. AI generates a natural language answer: "There are 4 high-risk reports at Metro Industrial Park, all classified as Electrical hazards."

This makes data accessible to non-technical users who don't know how to write SQL queries or use filters.

4.13 PDF Export

What it does: Generates a formatted report document (downloadable via browser) containing all key metrics. Useful for management reviews, safety audits, and regulatory submissions.

Contents

  • Summary stats: Total reports, high-risk count, unresolved high-risk, pending action
  • Unresolved high-risk items table: Site, category, reporter, date, status, justification
  • Top 5 riskiest sites ranked by high-risk report count
  • Footer with generation timestamp in IST

4.14 Multi-Tenant Organization Support

What it does: A global organization selector in the navbar filters all data by organization. Multiple companies can use the same SafeSignal instance without seeing each other's data.

How It Works

  • Every report, site score, and SMS recipient can be linked to an Organization
  • The org selector passes ?org=ID as a query parameter to every page
  • Server-side queries filter by organizationId when an org is selected
  • "All Organizations" shows data across the entire system

4.15 Human Risk Override

What it does: Safety officers can override the AI's risk classification with their own judgment. This acknowledges that AI isn't perfect and experienced humans may catch nuances the model misses.

How It Works

  • On the report detail page, click "Override risk" to change the classification
  • The override is stored in humanOverrideRiskLevel and overrideReason
  • The report table shows an "override" tag next to the risk badge when a human has changed the AI's assessment
  • The original AI classification is preserved in riskLevel for comparison
  • All overrides are logged to the AuditLog with the reviewer's name

7. Complete Data Flow

End-to-End: Report → Resolution

1. WORKER FILES REPORT
   POST /api/reports { reportText, site, reporterRole, isAnonymous }
   → Record saved to SafetyReport (status: pending)
   → AuditLog entry created

2. AI ANALYSIS (fire-and-forget background job)
   → Groq AI classifies: risk_level, hazard_category, justification
   → If all models fail → fallback keyword classifier activates
   → SLA deadline calculated (24h / 72h / 7d)
   → Key phrases extracted and stored
   → Report status updated to "analyzed"
   → AuditLog entry created

3. SMS ALERT (if high risk)
   → Query SmsRecipient WHERE category = report.category OR "All Categories"
   → If no matches → fallback to SAFETY_OFFICER_PHONE
   → Send via Textbee SDK to all matched phone numbers
   → AuditLog entry: "SMS sent to [department names]"

4. TASK GENERATION
   → Groq AI extracts 1-3 corrective tasks
   → If AI fails → fallback task generator by hazard category
   → Tasks auto-assigned to matching department
   → AuditLog entry: "Auto-generated N task(s)"

5. ADMIN MANAGEMENT
   → Kanban board: Open → In Progress → Done
   → Manual task assignment and priority override
   → Risk override with reason logging
   → All changes tracked in AuditLog

6. MONITORING & ANALYTICS
   → Dashboard: anomaly detection, escalation scores, compliance
   → Scoreboard: site safety scores (0-100)
   → Alerts: stale high-risk reports (48h+)
   → PDF export for reporting

7. RESOLUTION
   → Status changed to "resolved"
   → SiteScore recalculated
   → Resolution time tracked for speed bonus
